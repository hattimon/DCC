# Container web panels

DCC Web 0.3.2 separates a service address from its opening URL. Labels and **Copy panel address** retain the original service host and published TCP port. Local HTTP and HTTPS entry opens that address directly. Public entry uses the current DCC origin, including its protocol and port, plus `/panels/view/...`. A link contains identifiers, never a login credential.

Set the Docker host's reachable LAN address in **Profiles → Advanced → Panel address / host IP**. For the default local host, **Settings → Panel access and HTTPS → Panel addresses** also supplies the local address. DCC never substitutes the public browser hostname for a wildcard Docker binding. If the address is unknown, the container row asks for configuration. Explicit interface bindings retain their address, including IPv6 and loopback.

**Automatically open remote panels through DCC Web** is a global administrator setting in **Panel access and HTTPS (TLS)**. It defaults on with configured HTTPS/public-domain/Remote Access and preserves an explicit off/on choice across restarts and upgrades. Disabling it leaves the original direct address; it never constructs `public-domain:service-port`. A configured local name or private IP stays direct even under HTTPS. Other allowed public hosts use the gateway. Host validation and authenticated proxy/TLS detection are unchanged; arbitrary forwarded headers cannot change the selection. Configure unusual local DNS names explicitly as the local address.

## Transport and authorization

Each HTTP request reselects the exact full container ID and a stable panel identifier from the live published ports. Recognized HTTP ports and catalog-defined host-network panels are eligible. A caller cannot supply a target host, URL or arbitrary port. Paths, redirects and request headers are restricted; off-service redirects are blocked. A shared link requires the recipient's own active DCC session, completed 2FA where enabled, and current profile read permission.

With DCC Web in Docker on the local socket, a temporary restricted relay connects to the published port inside the selected container. This covers bindings on the host's `127.0.0.1` and separate Compose networks. The relay has no listener or Docker socket, and DCC Web does not join the project network. Docker TCP profiles and host-network panels still need a route to their published address. SSH/Balena profiles use the existing verified SSH authentication and `direct-tcpip` channel; wildcard bindings resolve to remote loopback, explicit bindings to their published interface. SSH forwarding must be permitted. HTTPS upstream certificates are verified.

WebSocket and SSE use scoped, session-bound server connections and short authenticated browser polling. No public WebSocket listener, provider-specific tunnel or new host agent is required. Every read/write operation rechecks login and profile permission. An independent one-second monitor closes idle connections after session expiry, logout/revocation, 2FA changes, profile-access removal or disabling the feature; operating-system scheduling can add delay. Profile/host configuration changes invalidate their contexts too. Already displayed information cannot be recalled. Direct LAN access remains controlled by the service itself.

## Isolation and service login

The outer DCC wrapper is trusted. Upstream documents are JSON/base64 data, parsed in an inert template, then executed only in an iframe sandbox without `allow-same-origin`, popups or top navigation. Its CSP blocks direct networking; a MessageChannel broker permits only the selected service. Panel JS cannot read the DCC document, storage, cookies or CSRF token. The broader CSP needed for panel scripts/styles applies only to this wrapper, not DCC administration pages.

Service cookies stay in memory on the server, keyed by DCC login session, profile, container and panel. They are never DCC session cookies and are not shared between users or panels. The bridge exposes only non-HttpOnly service cookies to panel scripts. Ordinary CSRF checks apply to every gateway mutation; there is no exception for missing or `null` Origin. Upstream service CSRF values and Authorization headers supplied by that service travel inside the scoped envelope. Service login is separate from DCC login. Restarting DCC or expiring its session requires signing in to the service again.

Only open services you are authorized to operate: profile read permission allows interacting with that service's own web UI, whose own authorization determines available actions. DCC does not turn upstream GETs into read-only service access. The iframe can communicate with its selected service and display that service's data, including personal data. It does not protect a service from its own administrator, an already compromised upstream application, or a privileged Docker/OS administrator.

## Compatibility and resource limits

Supported: classic JS, stylesheets/CSS URLs, images, same-service API via fetch/XHR, ordinary forms, multipart upload, downloads, service-cookie login, SSE and text/binary WebSocket messages. ES-module graphs, cycles, literal dynamic imports, basic import maps and `import.meta.url` are materialized as iframe-local blob modules using a vendored, MIT-licensed syntax parser. Upstream code never runs in the trusted wrapper.

This is an isolated compatibility gateway, not a full browser origin. Computed dynamic imports, scoped import maps, synchronous XHR, service workers, cross-origin OAuth/payment/CDN redirects, nested frames, WebRTC, native location-based routing and applications needing persistent browser-origin storage may require service base-URL configuration or a dedicated reverse proxy/VPN. Sandboxed storage is temporary. Code-generated resource URLs must use supported element setters/fetch APIs. Direct data/blob download links work inside the sandbox. The EventSource bridge ends when the server closes its stream; it does not implement automatic native reconnect/Last-Event-ID replay. WebSocket close-code details and XHR progress/streaming semantics are simplified. Unsupported features are not a claim of full compatibility with every container panel.

Limits: 1 MB decoded uploads/messages, 16 MiB responses, 8-second connect/read inactivity timeout, 30-second finite response transfer, 10-minute live connection lifetime, 30-second live polling inactivity, 1 MB queued output, 4 live connections per user/32 total, 256 in-memory panel contexts and 100 cookies per context. Module graphs allow 128 modules/4 MB source; document preparation allows 160 direct resources. Long-lived panels may need refreshing after a connection limit is reached. Native streaming downloads, very large uploads and media seeking may need direct LAN/VPN access.

Validation and deployment gaps for the current local candidate are recorded in `DCC_WEB_0.3.2_CONTINUATION.md` at the repository root. No test against a synthetic service certifies an existing production service, public certificate or external tunnel.
