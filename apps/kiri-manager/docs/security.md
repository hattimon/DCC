# Security

DCC Kiri Manager uses one administrator account. An unconfigured local installation allows `admin / admin` to open the password setup form for ten minutes. Set a new password and optionally a different username before connecting to panel data. The initial claim is atomic. The startup log prints the temporary credentials while the account is unconfigured.

Browser setup checks the direct peer for loopback or the host's IPv4 bridge gateway. Publish the container port on the host loopback as shown in the Store and Compose configuration. Deployments with `KIRI_PANEL_ORIGIN` use terminal provisioning with `python -m backend.admin`. The command supports an interactive password or a private stdin stream. It stores a scrypt password hash and can revoke sessions on reset. [Terminal setup and reset](installation.md#terminal-setup-and-password-reset).

The web endpoints use signed HttpOnly, SameSite=Strict cookies and digested server-side session IDs. Sessions expire after eight hours or on sign-out, password reset or process restart.

- Local HTTP is suitable for a loopback-published port. Configure `KIRI_PANEL_ORIGIN=https://panel.example` for a trusted, explicitly deployed reverse proxy. Preserve the external Host header and strip untrusted proxy headers. This setting enables Secure cookies and HSTS. Keep the origin port bound to loopback.
- Every data endpoint requires a session. A completed sign-in or successful account setup initiates one. Requests that change state require the exact origin and CSRF token. The liveness response contains only a fixed status.
- The login gate bounds both verification concurrency and attempts. Response bodies, upstream read deadlines and simultaneous calls are limited. Engine failures return diagnostic codes without upstream payloads.
- Socket profiles select only administrator-configured `KIRI_SOCKETS` aliases; arbitrary paths, direct Engine TCP and default Docker socket aliases are forbidden. SSH profiles use Paramiko RejectPolicy, a verified exact host/port key, no agent or implicit keys, and only the fixed command `docker system dial-stdio`. SSH transport requires network reachability and an already authorized remote account. Engine requests use a finite allowlist and validated IDs. Identity is rechecked on each operation, including socket inode and Server header; SSH writes use a single verified stream without reconnect.
- A dedicated Kiri socket grants sensitive engine access. The container definition drops all capabilities, uses `no-new-privileges` and a read-only filesystem, and adds only the socket's group when explicitly configured. A read-only bind mount still permits API writes through the socket. Restrict the panel's host and volume to trusted administrators.
- Inventory projections exclude environment variables, commands, raw host paths, arbitrary labels, warning messages and network addresses of connected containers. User-approved log reads are bounded and common secret formats are masked. Application logs omit these lines, but the authorized UI can still render unrecognized secret formats in an application's output.
- The Linux installer is an optional host-side command. It validates a pinned upstream package and uses the operating system's authorization mechanism. Its explicit panel access option registers a dedicated non-login host account with Kiri for the container's host UID. To revoke engine access, remove that account from the host's `kiri` group. The panel itself has no host-shell route and stores no installer credentials.

The app provides local socket and explicitly configured SSH connections. Only trusted administrators may use the panel: Engine access can control other workloads and remote SSH is an outbound network capability. A host user with administrative access or a process able to replace the configured socket is inside the trust boundary. If Kiri uses a new identity format, verify its release before changing the connector.

## Credentials and management

SSH secrets are Fernet ciphertext in SQLite; the local master key is separate from the database but in the same restricted data volume. This protects database-only copies, not an attacker with the entire volume or host privileges. Back up the key securely and separately; loss of the key with stored credentials fails closed. Never put credentials in URLs, logs or profile exports. Use HTTPS for access outside loopback. Verify the host key fingerprint independently (do not trust an unverified scan). An edited host, port, username, engine type or known_hosts entry requires fresh credentials. Paramiko protocol logs are suppressed and errors are sanitized.

The panel authenticates writes and checks CSRF, active profile and revision. Removal requires typing the exact container name; volumes are preserved but the writable layer is permanently removed. The engine account's permissions determine whether each action is allowed. Socket group and UID are unchanged; no privileged container, arbitrary shell or host filesystem API is introduced. Do not automatically retry ambiguous writes. The server rejects management and SSH profile creation/testing in demo mode. Protect the entire volume, including migration backups.
